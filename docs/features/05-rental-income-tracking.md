# Feature: Rental Income Tracking

## 1. Feature Overview
The **Rental Income Tracking** feature provides property owners on Nibash with a dedicated, authoritative, and secure financial overview of the rent they have received from their rental properties.

Owners can inspect their earnings across three distinct hierarchical tiers:
1. **Overall Income:** Portfolio-wide aggregation of total confirmed rent received, rent received in the current calendar month, active income-generating contracts, and total revenue-generating properties.
2. **Per-Listing Income:** Breakdown of confirmed rent generated by each property owned, showing property photo, advertised monthly rent, contributing contracts, active leases, and date of the latest received rent payment.
3. **Per-Contract Income:** Breakdown for each individual contract/lease, displaying tenant identity and contact information, agreed lease terms, contract duration and status, total received rent, and confirmed payment counts.

In addition, owners have access to an itemized **Payment History Ledger** displaying individual verified rent transactions, coupled with intuitive **Date Filtering** (*All Time*, *This Month*, *Last Month*, *Last 3 Months*, *Last 6 Months*, *Custom Range*), property-level cross-filtering, and strict owner data isolation.

## 2. Existing Architecture & Integration Points
Nibash is built on a PERN (PostgreSQL, Express, React, Node.js) stack with raw SQL queries executed through the `pg` driver (no ORM).

### Database Schema Context
* `users`: Base user identities, emails, phones, and credentials.
* `owners`: Links `users(id)` to property ownership.
* `tenants`: Stores tenant profiles (`monthly_income`, `emergency_contact`).
* `listings`: Properties published by owners (`status`: `approved`, `occupied`, `waiting`, etc.).
* `terms`: Terms associated with a listing or agreement (`rent`, `electricity_bill`, `water_bill`, `service_charge`, `security_deposit`, `monthly_due_date`).
* `agreements`: Terms agreed upon for a signed contract.
* `contracts`: Active or past leases linking a listing, tenant, and agreement (`status`: `proposed`, `signed`, `active`, `completed`).
* `payments`: Payment records associated with contracts (`status`: `pending`, `confirmed`, `overdue`, `failed`; `paid_at`, `amount`, `payment_method`, `billing_month`, `due_date`).

### Architectural Fit
* **Backend:** Follows the established Route → Controller → Service → Database pattern. Routes are guarded with `authMiddleware` which verifies JWTs and attaches `{ id, email }` to Express's `req.user`.
* **Frontend:** Built with React 19, React Router v7, and Tailwind CSS v4, adhering to Nibash’s dark silver luxury aesthetic. API requests flow through the centralized `client/src/api/client.ts`.

## 3. Income Definitions & Accounting Rules

To prevent financial misrepresentation, Nibash enforces strict accounting distinctions between confirmed income, pending dues, deposits, and unverified claims:

| Financial Category | Include in Received Rent? | Rationale & Technical Enforcement |
|---|---|---|
| **Confirmed Rent Payment** | **Yes** | `payments.status = 'confirmed'`. Only funds confirmed via digital gateway or verified by the owner. |
| **Pending Payment** | **No** | `payments.status = 'pending'`. Outstanding rent bills generated for a billing month but not yet settled. |
| **Overdue Rent** | **No** | `payments.status = 'overdue'`. Rent whose due date has lapsed without payment confirmation. |
| **Failed Payment** | **No** | `payments.status = 'failed'`. Transactions rejected by the payment gateway. |
| **Unverified Cash Claim** | **No** | `payment_method = 'Cash'` and `status = 'pending'`. Tenant marked "Paid by Cash", but the owner has not confirmed receipt. Excluded until owner clicks "Confirm Payment". |
| **Expected Future Rent** | **No** | Income is never estimated by multiplying contractual monthly rent by lease duration. Only recorded payment rows are computed. |
| **Security Deposit** | **No** | Security deposits are contractual terms (`terms.security_deposit`) and tracked as a boolean fulfillment flag (`contracts.paid_security_deposit`), not as recurring rental income. |
| **Utility & Service Charges** | **Note on Data Model** | Nibash contracts generate monthly rent bills encompassing the monthly rent and fixed service fees (`amount = rent + bills`). The payment record does not itemize sub-components; the confirmed payment amount constitutes the total rental dues received for that period. |
| **Refunds & Reversals** | **Limitation** | The current database schema does not have a dedicated refunds/reversals ledger. |

## 4. Financial Calculations & Formulas

All financial calculations are computed via PostgreSQL aggregate functions (`SUM`, `COUNT(DISTINCT ...)`, `MAX`) rather than in-memory JavaScript loops, avoiding floating-point inaccuracies and preventing memory bloat.

### Formulas

1. **Total Rent Received ($R_{\text{total}}$):**
   $$R_{\text{total}} = \sum_{p \in P_{\text{owner}}} p.\text{amount} \quad \text{where } p.\text{status} = \text{'confirmed'} \ [ \land \ p.\text{paid\_at} \in [\text{from}, \text{to}] \ ]$$

2. **Current Month Rent Received ($R_{\text{current\_month}}$):**
   $$R_{\text{current\_month}} = \sum_{p \in P_{\text{owner}}} p.\text{amount} \quad \text{where } p.\text{status} = \text{'confirmed'} \ \land \ p.\text{paid\_at} \in [\text{start\_of\_month}, \text{end\_of\_month}]$$

3. **Income-Generating Listings Count ($L_{\text{income}}$):**
   $$L_{\text{income}} = \text{COUNT}(\text{DISTINCT } l.\text{id}) \quad \text{where } \exists \ p \in P_{l} \text{ with } p.\text{status} = \text{'confirmed'}$$

4. **Income-Generating Contracts Count ($C_{\text{income}}$):**
   $$C_{\text{income}} = \text{COUNT}(\text{DISTINCT } c.\text{id}) \quad \text{where } \exists \ p \in P_{c} \text{ with } p.\text{status} = \text{'confirmed'}$$

5. **Per-Listing Rent Received ($R_{l}$):**
   $$R_{l} = \sum_{p \in P_{l}} p.\text{amount} \quad \text{where } p.\text{status} = \text{'confirmed'}$$
   *Properties with zero confirmed payments return $R_{l} = 0$ rather than being omitted.*

6. **Per-Contract Rent Received ($R_{c}$):**
   $$R_{c} = \sum_{p \in P_{c}} p.\text{amount} \quad \text{where } p.\text{status} = \text{'confirmed'}$$

## 5. Backend API Contract

All endpoints are mounted under `/api/owners/me/income`, requiring Bearer token authentication via `authMiddleware`.

### 5.1. Overall Income Summary
* **Route:** `GET /api/owners/me/income`
* **Query Parameters:**
  * `period` (optional string): `all` (default), `this_month`, `last_month`, `last_3_months`, `last_6_months`, `custom`
  * `from` (optional string, `YYYY-MM-DD`): start date for `custom` period
  * `to` (optional string, `YYYY-MM-DD`): end date for `custom` period
* **Success Response (`200 OK`):**
```json
{
  "currency": "BDT",
  "period": "all",
  "from": null,
  "to": null,
  "totalRentReceived": 125000,
  "currentMonthRentReceived": 25000,
  "incomeGeneratingListings": 2,
  "incomeGeneratingContracts": 3,
  "activeContractsCount": 3,
  "totalOwnedListings": 4
}
```

### Error Responses
* `400 Bad Request`: Invalid date format or unrecognized query parameter.
* `401 Unauthorized`: Missing, expired, or invalid JWT.
* `403 Forbidden`: Authenticated user is not an owner, or user attempted to query listings or contracts belonging to another owner.
* `500 Internal Server Error`: Unexpected database error.

## 8. Date Filtering & Timezone Behavior
* All date filters operate on the actual confirmation timestamp `payments.paid_at`.
* Date ranges use UTC-normalized ISO date strings formatted as `YYYY-MM-DD 00:00:00` and `YYYY-MM-DD 23:59:59` to guarantee inclusive coverage of transactions across timezone boundaries.
* Presets dynamically compute boundary start/end timestamps based on the current calendar date.

---

## 9. Security, Authorization & Data Isolation
1. **No Client Trust:** The owner identity is derived exclusively from Express's `req.user.id`, sourced from the verified cryptographic JWT. Client-supplied user or owner IDs in query parameters or request bodies are ignored.
2. **Strict SQL Isolation:** Every SQL query joins `listings l ON l.id = c.listing_id WHERE l.owner_id = $1`. An owner cannot view or aggregate payments from any property they do not own.
3. **Cross-Owner Parameter Validation:** If an owner supplies `?listing_id=X` or `?contract_id=Y`, `validateOwnerResourceAccess` explicitly checks ownership in the database. If the resource belongs to another user, an immediate `403 Forbidden` error is returned.

---

## 10. Architectural Limitations
1. **No Refund/Reversal Model:** Nibash's database schema does not currently track partial refunds, chargebacks, or transaction reversals.
2. **Unitemized Rent Payments:** In the current payments table, payments record the total monthly due (`amount = rent + utility bills`). Itemized breakdown between utility bills and base rent per transaction is not recorded in the schema.
